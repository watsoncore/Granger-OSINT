# Granger-OSINT 3.0.0 — проверка Windows-релиза

Проверено 28 октября 2026 года. Модернизирован существующий Python/PySide6-проект: React-интерфейс встроен в Qt WebEngine, Python сохраняет владение чатом, инструментами, секретами и нативной Гермионой. Это отчёт о проверенных сценариях и границах проверки, а не заявление о доступности каждого внешнего сервиса.

- `dist/Granger-OSINT.exe`: **233 378 704 байта**, AMD64 / PE32+ / Windows GUI, версия **3.0.0**.
- SHA-256: `169f22ac32159194ef450e2ec1999fcc3d751f31f8a7f4282026b0109037a88e`.
- Исходники с собранным frontend и выбранными материалами QA: `dist/Granger-OSINT-source.zip`.
- Проверка фактического CArchive: **56 Python-модулей** совпадают с поставляемыми исходниками; **24 проверки** frontend, ресурсов персонажа и браузерного runtime пройдены.
- Launcher и Pet запущены из настоящего EXE с новым временным профилем и `PATH=C:\Windows\System32`; оба дождались реального React `ui_ready` и завершились с кодом 0. Python/Node для ядра EXE через PATH не требуются. Это не испытание на чистой виртуальной машине; внешние OSINT-окружения по-прежнему готовятся отдельно.
- Новое имя, иконка, Windows AppID, version resources и ярлык `Desktop/Granger-OSINT.lnk`. Внутренние AppData, vault targets и IPC сохранены для совместимости.

Настройки и зашифрованная переписка обычного профиля были побайтно сопоставлены с локальной резервной копией до первого обычного запуска новой версии: оба файла совпадали. Все сетевые сценарии ниже использовали отдельный QA APPDATA; действующий ключ прочитан штатным механизмом Credential Manager и в QA-профиль не записывался.

## Исследование и выбранная архитектура

Сопоставлены React в desktop container, Tauri/Python sidecar, Qt Widgets и Qt WebEngine/QWebChannel. Выбран Qt WebEngine с локальным React/TypeScript/Vite: сохраняются event loop, Python-контроллеры и прозрачный нативный PetWindow. Цена решения — Chromium и существенно больший EXE.

Изучены живые демонстрации, документация и действительные исходники shadcn/ui, assistant-ui, Motion, Radix, Lucide, Magic UI, Telegram Desktop и публичная галерея 21st.dev. В браузере дополнительно осмотрены shadcn Button, assistant-ui Thread с меню ответа и категория AI-chat 21st.dev. Реально установлены React/React DOM, Radix primitives, Motion, Lucide, react-markdown/remark-gfm, CVA и clsx. Композиция Button адаптирована из MIT shadcn/ui с атрибуцией; Telegram, assistant-ui и платные gallery/Pro блоки не копировались.

Первичные URL, лицензии и обоснование каждого решения: [frontend/RESEARCH.md](frontend/RESEARCH.md). Тексты лицензий production frontend генерируются из locked dependency tree и включены в EXE. Qt/PySide/Shiboken/Chromium имеют собственные условия; копии и происхождение находятся в `resources/third-party/` и [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). Права на исходную фанатскую графику отдельно не расширяются.

## Автоматические проверки

- Python: **539 passed, 1 skipped, 32 subtests passed**, 80,94 с. Единственный пропуск — локальный Ollama не запущен; он не установлен и не загружался ради проверки. Лог: `output/upgrade-qa/tests-verified.log`.
- Frontend: **33 passed**, 5 файлов; TypeScript/Vite build успешен. В числе проверок — задержанные на 65 с экспорт/подтверждение инструмента и их отмена, штатный 30-секундный deadline других действий, ошибки bridge и отсутствие мнимого подключения вне desktop.
- Agent fixtures проходят **18 вызовов / 19 модельных раундов** сверх старых 10/14 ограничений и отдельный 36-этапный сценарий сжатия. Это контролируемые fixtures, не оплаченный live-запуск такой длины.
- Resume проверяет готовые и ожидающие вызовы, cache/deduplication, неизменный пользовательский бюджет, прерванный dispatch и no-progress guard. Неизвестный исход уже отправленного вызова не изображается успешным и не повторяется молча.
- Три новые Qt-регрессии проверяют первый API-сбой агента: один реальный запрос учитывается один раз, checkpoint привязан к сообщению, восстановленный диалог может продолжить первый неудачный этап. Ordinary-chat error также учитывается один раз.
- **24 проверки уведомлений** включают анимацию, прозрачность/чёткие пиксели, hit area, drag, виды событий, дедупликацию, настройки, docking и QTest-клик с восстановлением настоящего зашифрованного разговора в существующей панели.

## Сохранность и ограничения

- **Все 12 защищённых файлов персонажа совпадают с baseline побайтно.** Внешность, одежда, атласы и исходные animation definitions не перегенерировались.
- WebChannel доступен только локальному frontend. Удалённая навигация/загрузки/permissions/file pickers в renderer отклонены; HTML и удалённые картинки Markdown не выполняются/не загружаются. Секреты вводятся в сохранённой нативной форме и хранятся в Windows Credential Manager.
- Проверка точных байтов сохранённого ключа и credential-shaped strings охватывает исходники, историю Git, QA-тексты, EXE и распакованный source ZIP. Отчёт содержит только результат и имена нарушений, без ключа. Это специализированный скан, не общий security audit всех зависимостей.
- Нет live-подтверждения баланса шлюза и размера контекстного окна. UI честно показывает отсутствие данных. Общие бюджеты по умолчанию0; индивидуальные timeout, конечный контекст, checkpoint size и защита от циклов остаются.
- Обычная история наследует предел300 сообщений/24 реплики контекста; при большом объёме архив сокращает полные сообщения до60. Это не бесконечная память. Редактируемые Canvas и экспортированный Markdown — обычные локальные файлы.
- `web_read` остаётся HTTP-reader **без исполнения JavaScript**. Chromium интерфейса не открывает OSINT-страницы. CAPTCHA/paywall/403/429/авторизация и JS-only содержимое не обходятся и не объявляются прочитанными.
- Telegram/VK и прочие источники с авторизацией не объявляются проверенными без соответствующей сессии. Доступность внешнего сервиса меняется; локальный readiness не гарантирует результат.
- Физический CUA-клик отдельного письма пока не подтверждён: попытки через отдельную transient-область CUA не подтвердили переход к точному ответу. Производство живого уведомления и QTest routing с настоящим DPAPI-разговором проверены; это разные уровни проверки.
- Нет нового графа React Flow, полной виртуализации всех сообщений или измеренного performance benchmark. Renderer объединяет обновления и сохраняет неизменные сообщения, но очень длинные диалоги требуют дальнейшей проверки нагрузки.
- Локальная Windows-сборка и тесты пройдены. Успех GitHub Actions/подпись EXE/испытание на другом компьютере этим отчётом не утверждаются. Исходники публикуются обычными коммитами без force push; исполняемый файл и source ZIP доступны локально в `dist/`.
