# Маршрутизация и выдача GrangerPet — исправления

Работа выполнена в существующих `grangerpet/engine` и адаптерах. Исходный Gansar, сторонние папки и спрайты не изменялись.

## Детерминированный маршрут

`router.detect_query` отделяет очистку, проверку специализированного формата, неоднозначность и выбор категории. Для обычного имени не вызывается ИИ и не запускается поиск до выбора пользователя. `solvnox` предлагает «Публичные профили» или «Упоминания». Выбор относится к текущему запросу.

| Ввод | Проверка и нормализация | Адаптер |
|---|---|---|
| TON EQ/UQ/raw | Настоящий `Gansar-main/app/utils/ton_normalize.py::parse_ton_address`: Base64, tag, длина, CRC16, workchain; итоговый raw | Только `blockchain` → Gansar analyzer |
| TON testnet | Tag проверяется, test-only не теряется при переводе в raw; текущие mainnet-провайдеры не вызываются | Понятная ошибка, testnet не заявлен |
| TON DNS | В данном пути Gansar нет прямого разрешения `.ton` | Понятное ограничение; адрес не выдумывается |
| Никнейм после выбора пользователя | Один идентификатор без пробелов | Один готовый движок: Maigret, затем Blackbird, Social Analyzer; Snoop только если включён |
| Упоминания/Google Dork | Проверка синтаксиса операторов | Google API, либо явно обозначенное открытие браузера без встроенной выдачи |
| Email | Синтаксис local-part, длина и IDNA-домен | Holehe |
| Международный телефон, включая +7 | `phonenumberslite` — проверка допустимости и плана нумерации, E.164 | PhoneInfoga |
| Telegram `t.me/name`, публичная публикация | HTTP(S), допустимое публичное имя, запрет частных приглашений; `/s/` нормализуется | Telethon; без сессии `auth_required`, для конкретной публикации `get_messages(ids=...)` |
| VK `vk.com`, `m.vk.com`, id/club/public/event | Публичный URL/идентификатор, единый hostname | Только vk_api |
| Instagram публичный профиль | Публичное имя и разрешённый hostname | Instaloader |
| HTTP(S) URL / однозначный домен | Нормализация URL/IDNA, исключение локальных адресов | Только WaybackPy |
| Текст с точкой, похожий на никнейм | При неоднозначном суффиксе запрашивается направление | До выбора источники не запускаются |
| Другие ранее поддержанные блокчейн-форматы | Маршрут к имеющемуся ядру; фактические форматы и кандидаты проверяет Gansar | Только Gansar; новые сети не добавлены |

В EXE включён только исходный stdlib-валидатор TON из текущего Gansar. Аналитические библиотеки и пользовательские базы остаются внешними. Внешние интерпретаторы изолированы от Qt/PyInstaller DLL, секреты передаются через stdin, не через командную строку.

## Почему старый экран выглядел как «найдено 3» и три статуса

В прежней панели счётчик вычислялся из `_records`, но сами найденные карточки находились ниже встроенной длинной формы подключений и списка строк выполнения. Пользователь видел строки `_source_status`, а находки были вытеснены за область просмотра. Простая смена цвета не исправляла эту структуру.

Дополнительно граница модели была слишком мягкой: `Result.from_dict` подставлял тип, название, платформу и id для произвольного словаря, поэтому некорректный словарь состояния мог стать псевдорезультатом. Теперь `SearchResult` (совместимое имя `Result`) требует явные поля фактического объекта. Веб/профиль требует допустимый исходный URL; структурированное наблюдение — реальный id. `queued/running/complete/empty/error/...` не являются статусами подтверждения находки. `SourceExecution` — отдельный класс и отдельный сигнал.

`SearchSummary.result_count` — число уникальных нормализованных объектов. `confirmed_count` считает подтверждённые источником статусы; `uncertain_count` отдельно сохраняет эвристики, метки/связи с необходимостью проверки. Число выполненных источников хранится в `checked_sources`, не прибавляется к находкам.

Дедупликация учитывает tracking-параметры, hostname/scheme и известные варианты публичных профилей. Одинаковое имя на разных сайтах не объединяет людей. Файловые URL сохраняют регистр значимых частей пути. Разные балансы, транзакции, атрибуции и связи на одной explorer-странице остаются разными наблюдениями. Подтверждения разных движков сохраняются.

## Ошибка, обнаруженная реальным TON-поиском

Настоящий Gansar возвращает `details.confirmations` как число или `None` для подтверждений сети. Старый `ResultIndex` использовал то же имя для словаря подтверждающих источников. При поступлении промежуточной и окончательной версии одной транзакции координатор падал с `AttributeError`, а интерфейс мог оставаться в поиске. Теперь служебное доказательство хранится в `source_confirmations`, не изменяя сетевой счётчик. Добавлен регрессионный тест для `None`, 0 и 42; после исправления реальный TON-поиск завершился.

## Отмена и процессы

Каждый поиск имеет поколение `generation`; `search_event(generation, kind, payload)` проверяется при отправке и при получении UI. Новый поиск отменяет предыдущий, старые находки не смешиваются с новым запросом. После нажатия «Остановить» новые результаты отменённого поколения не принимаются. Холодные проверки зависимостей тоже получают тот же cancellation Event.

Все readiness-пробы и реальные источники делят один глобальный лимит двух дочерних процессов. Сама проверка готовности также использует две задачи и выдаёт фактические строки постепенно через callback: итоговый живой прогон 11 локальных окружений занял 7,81 секунды. Импорт источников идёт в отдельном интерпретаторе, с настоящими зависимостями и локальными базами, в временном cwd; одна папка не даёт статус «подключено». Доступность аккаунта не объявляется по факту наличия сохранённого токена. `stderr` дренируется без передачи чувствительного текста, учитываются ограниченный объём вывода и exit code. Отмена/таймаут завершает процесс и его потомков через Windows Job Object.

Gansar вызывается через `analyze_address(..., defer_graph=True)`. Стадии `routing`, `collectors`, `source`, `inference.frontier` и `analysis` передаются только из фактического callback ядра, без таймера. Достигнутый HTTP-бюджет и ошибки провайдеров обозначают неполноту, не мнимое полное исследование.

## Практические проверки

- Все 11 локальных runtimes реально импортировали свои модули; PhoneInfoga bridge был запущен с зарезервированным примером. Telegram/VK без ключей имеют `auth_required`; права реального аккаунта не проверялись. Отчёт: `output/search-overhaul-qa/readiness-live.json`.
- Реальный контроллер для `solvnox` после выбора публичных профилей запустил только Maigret и проверил 20 площадок. На момент проверки источник вернул 5 уникальных profile-URL с HTTP 200 и site-specific правилом детекции; 3 проверки были недоступны. Это не установление личности/владельца и не заранее ожидаемое число. Статус выполнения — неполное исследование. При следующем запуске выдача может отличаться.
- Реальный TON EQ-адрес с нулевым hash прошёл CRC-проверку, преобразовался в raw и вызвал только Gansar. После исправления коллизии `confirmations` пришли 12 уникальных наблюдений (10 подтверждённых источником транзакций и 2 метки/связи с пометкой проверки); получены настоящие стадии ядра. Выдача сохранена вместе с URL/датами/источниками, без вымышленных данных.
- Отчёт реальных сетевых запросов: `output/search-overhaul-qa/router-live.json`. Скрипт `scripts/verify_router_live.py` выполняет настоящие ограниченные запросы, а не fixtures; его запуск является явным действием.
- `tests/test_query_router.py` и существующие тесты движка проверяют действительный выбор адаптеров A–F, неверный TON CRC/testnet, неоднозначность, отдельные executions/results, дедупликацию/точный счётчик, замену/отмену, холодную readiness-отмену и общий лимит процессов. Эти тесты явно используют fixtures и не объявляются проверкой внешних аккаунтов.

Живые Telegram/VK/Instagram с пользовательской авторизацией, Google API с ключом и Gemini/Ollama в этой проверке не тестировались. Проверка готового EXE, GUI и физических реакций проводится отдельно и описывается в общем отчёте сборки.
