# Native WebEngine CPU diagnostic A/B

Эти результаты локализуют нативный расход CPU и **не означают завершения оптимизации**. Повторные проверки старого и финального EXE ниже воспроизвели как высокий, так и низкий расход CPU. Причина разброса не установлена; однозначный вывод о регрессии обновления или полном исправлении делать нельзя. Диагностические варианты не переносились в production: точная alpha-mask, глобальные GPU-флаги, драйверы и другие приложения не менялись.

## Метод

`scripts/qa_native_cost.py` создаёт настоящий source PetWindow и workspace в изолированном APPDATA. Пустой переносимый vault имеет уникальный тестовый namespace; реальные секреты/API не используются. Чат содержит 1000 явно синтетических записей. Каждый вариант измеряется 6 секунд после паузы 1.5 секунды. ProcessSampler учитывает только точный текущий Python PID и его подтверждённых потомков. Windows GetThreadTimes/GetThreadDescription читаются только для потоков текущего PID.

Операции A/B выполняются лишь над собственными Qt объектами в QA-процессе и отменяются после измерения. Фиксированная маска — исключительно диагностический вариант, не допустимая производственная замена точного click-through.

Дополнительная `ProbeApplication.notify` собирает только class/type/count/duration. Имена объектов, пользовательские тексты и содержимое событий не записываются. Длительности включают вложенные события, поэтому их нельзя суммировать как независимое CPU-время.

## Важное различие event loop

Первоначальный `QTest.qWait` вариант дал 10–14% одного ядра при видимом чате и около 10% при свёрнутом окне. Эти абсолютные цифры **несопоставимы** с настоящим Qt event loop. Переключение harness на `QEventLoop.exec()` воспроизвело повышенный CPU около 30–40% и снижение до 7% при сворачивании. Ранние результаты с QTest не доказывают устранения проблемы и не используются как релизный результат.

## Результаты с Qt event loop

Команда:

```powershell
.venv\Scripts\python.exe scripts/qa_native_cost.py --output output/reconstruction-qa/native-cost-qtloop-full --event-loop qt
```

Медиана шести сэмплов; 100% означает одно логическое ядро.

| Вариант | CPU одного ядра |
|---|---:|
| Исходный видимый чат, анимированный Pet | 38.71% |
| Таймеры Pet остановлены, изображение остаётся | 26.13% |
| Pet скрыт, workspace видим | 29.06% |
| Pet скрыт, убраны QSS приложения и панели | 26.25% |
| То же, системный шрифт Segoe | 30.86% |
| Восстановлены обычные настройки | 31.52% |
| Белый backgroundColor страницы | 34.26% |
| Явно открыта правая панель, анимация | 42.59% |
| Маска временно фиксирована только в QA | 30.26% |
| Точная динамическая маска восстановлена | 30.42% |
| Панель персонажа явно свёрнута | 29.46% |
| Workspace свёрнут, Pet продолжает анимацию | 6.96% |
| WebEngine widget скрыт, Pet остановлен/скрыт | 0.76% |
| WebEngine widget снова показан, Pet скрыт | 0.77% |

На первом видимом варианте поток с описанием **CrBrowserMain** потреблял 27.55% одного ядра, ещё один поток текущего процесса — 11.84%. После остановки таймеров Pet CrBrowserMain всё ещё потреблял 18.59%; после скрытия Pet — 22.49%. Обычные Qt notify события в вариантах без таймеров Pet заняли менее 1 ms за 6 секунд, при этом процесс оставался нагружен. Это указывает на работу нативного Chromium pump вне обычных обработчиков QWidget, а не на повторную Python сериализацию истории.

Отдельный Qt-loop A/B с **работающими** таймерами Pet:

| Вариант | CPU одного ядра |
|---|---:|
| Текущие QSS/шрифт/palette | 37.50% |
| Без QSS, текущие шрифт/palette | 43.22% |
| Legacy STYLE, текущая palette | 31.77% |
| Legacy STYLE/palette и Segoe | 31.21% |
| Текущий STYLE, legacy palette/Segoe | 29.41% |
| Всё восстановлено | 35.91% |

Эти варианты не подтверждают QSS, текущую palette или установленный после регистрации шрифт как причину. Регистрация Manrope через QFontDatabase до создания WebEngine — отдельная ещё не исключённая гипотеза; harness поддерживает `--system-font-only`, чтобы пропустить её **до** создания приложения.

## Исторические диагностические гипотезы

- Прежний EXE `d8994e…` проверен в той же текущей среде; результаты приведены ниже.
- Воспроизведение на обычном `app.exec()` через `scripts/perf_source_probe.py` подтвердило нативный расход; опция `GRANGERPET_PERF_NOTIFY=1` включает только QA class/type счётчики.
- Проверить skip регистрации native Manrope до запуска WebEngine одним отдельным вариантом.
- Проверить жизненный цикл видимости WebEngine после initial show: hide/show в этом QA run оставил нагрузку низкой даже после повторного показа. Это наблюдение, а не доказанная причина или готовое исправление.

Нельзя выпускать постоянную остановку анимаций, фиксированную неточную маску или глобальное отключение GPU как «исправление» на основании этих измерений. Контрольные запуски дают высокий и низкий CPU на обоих бинарниках; причина межсессионного изменения WebEngine остаётся неустановленной.

## Повторная проверка сохранённого EXE в текущей среде

Сохранённый настоящий EXE d8994ea90eb62c600ed8218d8a4a944e69af94d7468a9c3a7fa37cbf14396ddb повторно запущен через ту же QA-команду, тот же синтетический профиль 1000 сообщений и те же настройки среды:

- старый EXE, видимый workspace: **28.6586% одного ядра**, RSS516253696 байт;
- старый EXE, свёрнутый: **5.4204%**, RSS516884480 байт;
- кандидат обновления, видимый: **30.2044%**, RSS494825472 байт (3×6 с);
- кандидат обновления, свёрнутый: **6.1970%**, RSS496062464 байт.

Старый repeat — один 6-секундный trial; кандидат — медиана трёх. Эти данные не доказывают новую CPU-регрессию от UI/character/vault, и исторические 6.2% из другой сессии нельзя использовать как строго сопоставимый baseline. В текущей среде высокий нативный расход воспроизводился и до обновления; следующие повторные запуски ниже также показали низкий расход обоих EXE. Точная причина межсессионного изменения WebEngine не установлена; другие приложения и настройки системы не исследовались ради её поиска.

Постоянные изменения FPS, масок, GPU-флагов или жизненного цикла ради скрытия этого результата не внесены. Финальный EXE повторно измерен отдельно; источник сырых данных — performance-old-recheck/report.json и performance-long/report.json в output/reconstruction-qa. Предыдущая формулировка выше об открытой проверке регрессии относится к диагностическому кандидату и уточняется этим контрольным запуском.

## Финальные повторные измерения

Один и тот же финальный EXE `191bf4f33a968e5f30c9235abed821a5338c3f3af875cd00a6c97c7bde59afbe` дал 34.0741% видимого CPU в performance-release и 6.1932% в performance-release-repeat; оба — 3×6 с. Старый d8994e… в performance-baseline-matched дал 6.1966% видимого CPU (также 3×6 с), тогда как старый performance-old-recheck ранее дал 28.6586%. Все отчёты сохраняются. Нельзя выбрать только удобный прогон и заявить гарантированное ускорение.

В QA добавлена запись только булевых состояний собственных окон до/после trial: visible, minimized, принадлежность foreground своему процессу. Перед этим повторно проверяется образ PID. Имена, тексты, геометрия чужих окон и их foreground handle не записываются; фокус во время измерений не меняется. Это уточнение диагностического скрипта, не production workaround.


Финальное сопоставимое измерение с проверкой foreground собственных окон (по 3×6 с):

В каждом видимом trial до и после выборки foreground принадлежал самому Granger; в свёрнутых — нет. У обоих EXE по три процесса в рабочем состоянии и ноль после полного выхода. Новый RSS вырос примерно на 7.82 МиБ в последнем видимом сравнении. Результаты не устанавливают причину отдельных высоких прогонов и не обещают исправление микролагов. Новые JSON содержат булевую диагностику own_windows_before/after. Отчёты: `performance-focus-baseline/report.json` и `performance-focus-final/report.json`.

Время активного расследования, источников и стриминга отдельно после последней сборки **не измерено**; реальная успешность DeepSeek+инструментов проверена отдельным live agent smoke. Фактический DPR исходного native QA — 1.25; Windows scaling не менялся.
