# Native CPU regression diagnostic A/B

Эти результаты локализуют проблему и **не означают завершения оптимизации**. Производственные настройки, код рендера, точная alpha-mask, глобальные GPU-флаги, драйверы и другие приложения не менялись.

## Метод

`scripts/qa_native_cost.py` создаёт настоящий source PetWindow и workspace в изолированном APPDATA. Пустой переносимый vault имеет уникальный тестовый namespace; реальные секреты/API не используются. Чат содержит 1000 явно синтетических записей. Каждый вариант измеряется 6 секунд после паузы 1.5 секунды. ProcessSampler учитывает только точный текущий Python PID и его подтверждённых потомков. Windows GetThreadTimes/GetThreadDescription читаются только для потоков текущего PID.

Операции A/B выполняются лишь над собственными Qt объектами в QA-процессе и отменяются после измерения. Фиксированная маска — исключительно диагностический вариант, не допустимая производственная замена точного click-through.

Дополнительная `ProbeApplication.notify` собирает только class/type/count/duration. Имена объектов, пользовательские тексты и содержимое событий не записываются. Длительности включают вложенные события, поэтому их нельзя суммировать как независимое CPU-время.

## Важное различие event loop

Первоначальный `QTest.qWait` вариант дал 10–14% одного ядра при видимом чате и около 10% при свёрнутом окне. Эти абсолютные цифры **несопоставимы** с настоящим Qt event loop. Переключение harness на `QEventLoop.exec()` воспроизвело повышенный CPU около 30–40% и снижение до 7% при сворачивании. Ранние результаты с QTest не доказывают устранения проблемы и не используются как релизный результат.

## Результаты с Qt event loop

Команда:

```powershell
.venv\Scripts\python.exe scripts/qa_native_cost.py --output output/reconstruction-qa/native-cost-qtloop-full --event-loop qt
```

Медиана шести сэмплов; 100% означает одно логическое ядро.

| Вариант | CPU одного ядра |
|---|---:|
| Исходный видимый чат, анимированный Pet | 38.71% |
| Таймеры Pet остановлены, изображение остаётся | 26.13% |
| Pet скрыт, workspace видим | 29.06% |
| Pet скрыт, убраны QSS приложения и панели | 26.25% |
| То же, системный шрифт Segoe | 30.86% |
| Восстановлены обычные настройки | 31.52% |
| Белый backgroundColor страницы | 34.26% |
| Явно открыта правая панель, анимация | 42.59% |
| Маска временно фиксирована только в QA | 30.26% |
| Точная динамическая маска восстановлена | 30.42% |
| Панель персонажа явно свёрнута | 29.46% |
| Workspace свёрнут, Pet продолжает анимацию | 6.96% |
| WebEngine widget скрыт, Pet остановлен/скрыт | 0.76% |
| WebEngine widget снова показан, Pet скрыт | 0.77% |

На первом видимом варианте поток с описанием **CrBrowserMain** потреблял 27.55% одного ядра, ещё один поток текущего процесса — 11.84%. После остановки таймеров Pet CrBrowserMain всё ещё потреблял 18.59%; после скрытия Pet — 22.49%. Обычные Qt notify события в вариантах без таймеров Pet заняли менее 1 ms за 6 секунд, при этом процесс оставался нагружен. Это указывает на работу нативного Chromium pump вне обычных обработчиков QWidget, а не на повторную Python сериализацию истории.

Отдельный Qt-loop A/B с **работающими** таймерами Pet:

| Вариант | CPU одного ядра |
|---|---:|
| Текущие QSS/шрифт/palette | 37.50% |
| Без QSS, текущие шрифт/palette | 43.22% |
| Legacy STYLE, текущая palette | 31.77% |
| Legacy STYLE/palette и Segoe | 31.21% |
| Текущий STYLE, legacy palette/Segoe | 29.41% |
| Всё восстановлено | 35.91% |

Эти варианты не подтверждают QSS, текущую palette или установленный после регистрации шрифт как причину. Регистрация Manrope через QFontDatabase до создания WebEngine — отдельная ещё не исключённая гипотеза; harness поддерживает `--system-font-only`, чтобы пропустить её **до** создания приложения.

## Дальнейшая локализация

- Проверить прежний EXE `d8994e…` в той же текущей среде перед выводом о регрессии кода.
- Воспроизвести на обычном `app.exec()` через `scripts/perf_source_probe.py`; опция `GRANGERPET_PERF_NOTIFY=1` включает только QA class/type счётчики.
- Проверить skip регистрации native Manrope до запуска WebEngine одним отдельным вариантом.
- Проверить жизненный цикл видимости WebEngine после initial show: hide/show в этом QA run оставил нагрузку низкой даже после повторного показа. Это наблюдение, а не доказанная причина или готовое исправление.

Нельзя выпускать постоянную остановку анимаций, фиксированную неточную маску или глобальное отключение GPU как «исправление» на основании этих измерений. Релизная проверка CPU остаётся открытой до подтверждённого устранения и повторного замера настоящего EXE.
